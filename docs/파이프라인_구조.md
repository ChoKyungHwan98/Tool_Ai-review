# 파이프라인 구조와 운영 기준

## 기준 구조

현재 실행 경로는 `collect_reviews.py` → `analyze_reviews_v3.py` → `build_insights_v5.py`입니다. 서버와 화면은 `/dashboard/data/v5`만 사용합니다. 계산은 한 곳에서만 합니다: 표본 수식은 `sampling.py`, 건수·비율 집계는 `dashboard_evidence.py`. 버전이 다른 이전 실행 파일과 화면 분기는 저장소에서 제거했습니다.

## 분석 단계

| 단계 | 입력 | 처리 | 출력 |
| --- | --- | --- | --- |
| 수집 | Steam App ID, 언어, 표본 설정 | 모집단 조회, 표본 크기 계산, 리뷰 수집 | `reviews.csv`, `sample_design.json` |
| 주제 발견 | 리뷰 세 묶음(각 최대 100건, 서로 겹치지 않음) | 묶음마다 주제 후보를 찾고, 후보를 한 번 더 정리해 최대 14개로 확정 | `themes_v3.json` |
| 전체 분류 | 수집 리뷰 | 반응, 재미 유형, 주제별 긍정·부정, 한 줄 근거 | `analysis_v3.jsonl` |
| 불만 심층 | 불만 가능 리뷰 | 문제, 직접 언급한 원인, 사용자 요청 | `complaints_v3.jsonl` |
| 요약 | 위 산출물 | AI 요약 한 문단, 비추천 쪽으로 기운 주제의 문제·원인·요청 | `insights_v5.json` |
| 집계·점검 | 위 산출물 | 주제·플레이 시간·반응 건수, 자료 상태 점검(완전성·일관성·분석 가능성) | 저장하지 않음 (화면을 열 때 계산) |

## 주제 발견 규칙

- 묶음 하나만 보고 정하면 그 묶음에 우연히 많았던 말이 주제가 된다. 서로 다른 세 묶음에서 후보를 찾고, 여러 묶음에 나온 후보를 우선해 정리한다.
- 정리 단계에서 같은 문제를 가리키는 후보를 합친다(예: 저장 오류와 데이터 삭제). 자동 합치기 규칙은 "한 리뷰에 함께 붙은 주제"만 합치므로, 번갈아 붙는 같은 뜻의 주제는 여기서 합쳐야 한다.
- 느낌을 가리키는 이름(시간, 재미, 몰입, 중독 등)은 AI가 내더라도 규칙으로 뺀다. 주제는 게임의 구성 요소다.
- 주제 설명은 평가 없이 중립으로 쓰고, 분류 단계에 이름과 함께 준다. 낱말만 같은 다른 뜻("거점을 최적화")을 가려내기 위해서다.
- 주제 찾기 방식이 바뀌면 `THEME_VERSION`을 올린다. 예전 방식의 주제·분류는 `previous-themes-날짜` 폴더로 보관하고 같은 리뷰를 다시 분류한다.

## 반응 분류

- **긍정**: 좋았던 경험을 중심으로 말함
- **부정**: 불편이나 문제를 중심으로 말함
- **혼합**: 긍정과 부정이 한 리뷰에 함께 있음
- **판단 어려움**: 내용이 너무 짧거나 반응 방향이 명확하지 않음

Steam의 추천 여부는 사용자 행동 값이고, AI 반응 분류는 문장 내용에 대한 해석입니다. 화면과 집계에서 두 값을 구분합니다.

## 토큰 비용 통제

- 코드로 계산할 수 있는 추천률, 플레이 시간, 표본 수는 AI에 보내지 않습니다.
- 주제 발견 결과를 전체 배치에 재사용합니다.
- 긴 원문을 단계별 상한까지 자릅니다.
- 분류 결과는 짧은 키의 JSON으로 받습니다.
- 불만 심층 분석은 조건을 충족한 리뷰에만 실행합니다.
- 완료된 ID를 JSONL에서 읽어 남은 리뷰만 분석합니다.
- 모델 단가와 최대 출력 토큰을 기준으로 호출 전에 비용을 예약합니다.
- 예약 합계가 예산을 넘으면 새 호출을 시작하지 않습니다.
- v5 요약 입력이 같으면 캐시를 사용합니다.

## 모델 교체 원칙

모델이 바뀌어도 출력 계약은 같습니다. 모델 목록은 OpenRouter에서 읽고 무료·유료, 문맥 길이, JSON 형식 지원, 입력·출력 단가를 함께 표시합니다. 모델을 변경하면 이전 분석 산출물을 보관한 뒤 같은 단계로 다시 분석합니다.

## 무료 모델로 돌릴 때

무료 모델은 여러 사람이 같이 써서 수시로 요청을 거절한다(429, "rate-limited upstream"). 그래서:

- 고른 모델이 거절하면 대신 답할 무료 모델을 요청에 같이 적어 보낸다(OpenRouter의 `models` 배열, 최대 2개). 같은 회사 모델을 먼저, 그다음 이름에 적힌 크기가 큰 순서로 고른다. 작은 모델(20b 미만, nano·mini 등)과 OpenRouter 무료 라우터는 쓰지 않는다 — JSON 답이 중간에 끊긴다.
- 답 길이 한도를 네 배로 준다. 답을 쓰기 전에 "생각"에 토큰을 쓰는 모델은 한도가 빠듯하면 답이 비어서 온다.
- 요청은 한 번에 하나씩, 약 3.3초 간격으로 보낸다. 거절당하면 15초, 30초, 60초를 기다렸다 다시 묻고, 그래도 안 되면 쉬운 말로 알리고 멈춘다. 다시 실행하면 이어서 한다.
- 대신 답한 모델과 횟수는 `usage_v3.json`의 `stand_ins`에 남기고 분석 방법 화면에 적는다.
- 유료 모델은 대체하지 않는다(비용이 달라진다).

## 프로젝트 공개 시점

`games.json`에는 v5 분석이 완료된 게임만 표시합니다. 사용자가 새 분석 화면을 열었다가 아무 작업 없이 나가면 빈 프로젝트가 생기지 않습니다. 분석 성공 후 Steam 게임 정보를 불러와 목록에 추가합니다.

## 화면 데이터 계약

`GET /dashboard/data/v5`가 화면의 단일 기준입니다. 응답에는 다음 데이터가 포함됩니다.

- 게임 이름과 Steam 이미지
- 수집·분석 범위와 언어
- 전체 반응 분포
- 주제별 긍정·부정 언급 수
- 플레이 시간별 비추천 비율과 표본 수
- 플레이 구간별 불만 주제
- 주제별 상세 원인과 대표 리뷰
- 자료 상태 점검 (저장된 파일이 아니라 요청할 때 계산한 값)
- 리뷰 탐색용 분석 행

주제 원문은 `GET /dashboard/evidence`에서 페이지 단위로 읽습니다.

## Impeccable 적용 결정

- 설치 상태: 개인 Codex 스킬 4.3.1 정상 설치
- 적용 방식: 화면 구조, 반응형 배치, 초점 표시, 문구와 시각 계층 점검에 사용
- 저장소 포함 여부: 포함하지 않음
- 이유: 개발 작업을 돕는 도구이며 프로그램 실행에 필요한 라이브러리가 아님

## 유지보수 규칙

1. 새 분석 버전을 만들기 전에 현재 데이터 계약을 확장할 수 있는지 먼저 확인합니다.
2. 새 화면은 별도 이전 버전 분기를 만들지 않고 단일 엔드포인트를 갱신합니다.
3. 프롬프트는 모델 이름에 의존하지 않고 JSON 계약과 금지 추론을 명시합니다.
4. 집계 가능한 수치는 파이썬으로 계산하고, 의미 요약만 모델에 맡깁니다. 같은 수치를 두 곳에서 계산하지 않습니다. 화면(JS)도 식을 다시 쓰지 않고 서버 값을 읽습니다.
5. 화면이 쓰지 않는 값은 저장하지도 내려주지도 않습니다. AI를 부르는 단계는 화면에 결과가 쓰일 때만 둡니다.
6. 문서, 테스트, 다운로드 파일명, 화면 데이터 경로를 같은 변경에서 갱신합니다.
